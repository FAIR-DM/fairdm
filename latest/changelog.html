Changelog#

All notable changes to the FairDM project will be documented in this file.

The format is based on Keep a Changelog, and this project adheres to Semantic Versioning.

[Unreleased]#

Changed#

  • The documentation is published at https://docs.fairdm.org/. It was on Read the Docs, where the last build that succeeded was in April 2026. The User Guide and Admin Guide links in a portal’s Documentation menu, the User guide link in the landing page footer and the About portal roles link on the team page now point to it.

  • The documentation is versioned. latest/ follows main, each release from now on gets a folder of its own such as 0.4/, and a switcher in the site’s header moves between them. Page addresses gain latest/, and the links in a portal, the README and the package metadata point there.

[v0.3.1] - 2026-10-28#

Fixed#

  • A portal whose database predates the portal roles can run the upgrade commands before migrate. The start-up check fairdm.E500 refused every command except migrate while a role was missing, so upgrade_literature, upgrade_vocabularies and sync_vocabularies, which the upgrade guides run before migrate, stopped with “FairDM role(s) missing from the database”. The check now stands down for those three commands as well.

  • upgrade_vocabularies no longer fails on a model whose table does not exist yet. It asked the database to describe the table of every model with a concept field, and PostgreSQL raised relation ... does not exist for a table the portal’s pending migrations have yet to create. The command now skips such a model and such a through table, since migrate creates it with the new schema.

  • The two upgrade guides say the database must first be migrated with FairDM 0.2.1. The commands read tables and columns that an older database does not have yet. A container portal runs migrate in a one-off container of its previous image before it follows either guide.

[v0.3.0] - 2026-10-28#

Added#

  • A portal backs up its database and media every week with no configuration. The new fairdm.backups app creates two periodic tasks, one for the database and one for the media, on Sunday at 03:00 in TIME_ZONE. A schedule you change or a task you switch off is never reset. manage.py backup writes both backups now, or one with --database-only or --media-only. The settings BACKUP_DIR, BACKUP_KEEP and BACKUP_SERVER_NAME choose the directory, the number of backups kept of each kind and the server name in the file names. The runtime image carries postgresql-client-17 and the directory /var/lib/fairdm/backups. See How to back up a portal.

  • Backups are encrypted to a public key. With BACKUP_PUBLIC_KEY set to an armoured OpenPGP public key, each database and media backup is written as a .gpg file only the private key opens. The deployment checks fairdm.E700 (no key) and fairdm.E701 (not a public key that can encrypt, a private key, or no gpg) report the setting. The runtime image carries gnupg. See How to back up a portal.

  • Backups follow the media to S3, and the scheduler runs in the images. With the S3_* variables set, backups go to the media bucket under backups/, or to the bucket in the new BACKUP_S3_BUCKET_NAME, and the media archive leaves the backups out when they share a bucket. Retention only touches the backup location. The new warning fairdm.W700 reports a production portal that keeps backups on its local disk. The images start Celery beat with the new beat command, and the development compose file gains a celerybeat service and a backups volume. See How to back up a portal and How to deploy a portal in a container.

  • A portal restores from an encrypted backup with commands it already has. listbackups, dbrestore --decrypt and mediarestore --decrypt --uncompress --replace of django-dbbackup read the backups in a one-off container whose gpg keyring holds the private key, and a key that does not match stops the restore before anything changes. See How to restore a portal from a backup.

Changed#

  • FairDM is published to PyPI. Publishing a release uploads the package to PyPI, so a portal depends on fairdm from PyPI (uv add fairdm) rather than on a git source pinned to a release tag. The tutorial installs it that way.

  • Breaking for upgrades: production now requires BACKUP_PUBLIC_KEY, and a custom image needs gpg. A production portal with no key, or with a key that cannot encrypt, stops at start-up with fairdm.E700 or fairdm.E701. Set the variable to the armoured public key and install gnupg in an image you build yourself.

  • Breaking for upgrades: a portal’s own DBBACKUP_STORAGE or DBBACKUP_STORAGE_OPTIONS must move to STORAGES["dbbackup"]. django-dbbackup 5, which FairDM now requires at 5.3 or later, stops with an error when either setting exists. FairDM no longer sets them, so a portal that never set them has nothing to change. The default number of database backups kept falls from 10 to 4.

  • Breaking for upgrades: FairDM now installs django-literature 0.3.1 from PyPI, and references are literature.Item. Dataset.reference, Dataset.related_literature and DatasetLiteratureRelation.literature_item point at literature.Item in place of literature.LiteratureItem, so a portal that already holds references must move its database across with upgrade_literature before it migrates. The Literature entry of the main menu opens the catalogue, which now lives at /literature/ and not /django-literature/, and its add, edit, import and delete pages require the literature.add_item, literature.change_item and literature.delete_item permissions. django-select2 is no longer installed. LiteratureItemFactory builds an Item and takes doi, year and authors. See How to upgrade a portal to django-literature 0.3.

  • Breaking for upgrades: every controlled term is stored as the address of a concept in a published vocabulary. FairDM’s description, date and identifier types, contributor roles and sample statuses are the concepts of the vocabularies in FAIR-DM/fairdm-vocabularies, each at an address under https://w3id.org/fairdm/vocabularies/, and are held through django-controlled-vocabularies 0.3.1 from PyPI. Sample.status, the type of every description, date and identifier row, and ContributorIdentifier.type are ConceptFields limited to their record type’s collection, and Contribution.roles and the keywords of projects, datasets, samples, measurements and the portal identity are MultiConceptFields. Code that names a term names its address, through the constants in fairdm.core.vocabularies. A portal loads the vocabularies with sync_vocabularies, and a portal that already holds data converts it with upgrade_vocabularies before it migrates. FAIRDM_PROJECT["keywords"] lists the addresses of vocabularies, not Python classes, and no longer offers the contributor roles as keywords by default. The API gives a description, date or identifier type as its address, and a keyword’s vocabulary as the vocabulary’s address. The DataCite metadata still names each type and role as DataCite does. See How to upgrade a portal to vocabulary addresses.

Removed#

  • django-research-vocabs is no longer installed, and the migrations no longer refer to it. fairdm.core.vocabularies holds the addresses of FairDM’s vocabularies in place of its vocabulary classes. The unused choice lists in fairdm.core.choices and fairdm.contrib.contributors.choices are gone, as are GRID from the identifier resolvers and the FairDMIdentifiers duplicate in fairdm.contrib.contributors.choices.

  • Eleven runtime dependencies FairDM no longer uses are gone: django-admin-extra-buttons, django-braces, django-classy-tags, django-contact-form, django-extensions, django-markdownx, django-orbit, django-setup-tools, django-social-share, django-widget-tweaks and flower. With them go the contact page at /contact/ and its footer link, the Orbit dashboard at /orbit/ and its middleware, the markdown preview address /markdownx/markdownify/, and the settings DJANGO_SETUP_TOOLS, MARKDOWNX_MARKDOWNIFY_FUNCTION and ORBIT_CONFIG. A portal that imports or installs one of these packages itself now declares it as its own dependency. A portal that wants a markdown editor installs django-markdownx and points its preview at fairdm.utils.markdown.markdownify. A portal database keeps the orbit_orbitentry table django-orbit created. Nothing reads it, and python manage.py migrate orbit zero, run before upgrading, drops it.

[v0.2.1] - 2026-10-22#

Changed#

  • FairDM requires django-mvp 0.31 and django-mvp-forms 0.8.

  • The facts column on overview pages is a column of the page again. On project, dataset, sample, measurement, person and organization pages, the facts sit in a narrow column beside the content, as they did before v0.2.0, and stack after the content below the lg breakpoint. The “At a glance” side panel is gone. A template that overrides overview.side or a block inside it keeps working. One that filled page.side on an overview page should override overview.side instead.

Removed#

  • fairdm.contrib.theme is gone. It held nothing in use but the brand logo and icon, which now ship from fairdm/static/img/brand/ at the same paths, so a portal that replaces img/brand/logo.svg or img/brand/icon.svg keeps working unchanged. A portal that lists fairdm.contrib.theme in its own INSTALLED_APPS must remove it.

  • fairdm.contrib.generic is gone. TaggedItem, the model behind every record’s free keywords, moves to fairdm.models, and KeywordForm to fairdm.core.forms. The other forms in the app were used by nothing and are deleted, and FairDM no longer depends on django-extra-views. Running migrate renames the generic_taggeditem table to fairdm_taggeditem and keeps every keyword.

    Upgrading:

    1. Run python manage.py migrate. It records the new fairdm migration as applied, because your database already has the table, then renames the table and moves the model’s content type and permissions to the fairdm app.

    2. Remove fairdm.contrib.generic from INSTALLED_APPS if your portal lists it itself.

    3. Change from fairdm.contrib.generic.models import TaggedItem to from fairdm.models import TaggedItem, and from fairdm.contrib.generic.forms import KeywordForm to from fairdm.core.forms import KeywordForm. The other forms and formsets in that module are gone with nothing in their place.

    4. Search your own migrations for "generic". A dependency on ("generic", "0001_initial") keeps working, because Django maps it to the new migration. A field that names "generic.TaggedItem" must name "fairdm.TaggedItem" instead.

    5. If you use django-extra-views yourself, add it to your portal’s dependencies. FairDM no longer installs it.

[v0.2.0] - 2026-10-21#

Added#

  • FairDM declares the image and database a portal runs on. [tool.fairdm.platform] in pyproject.toml records the base image version (image) and the postgis/postgis tag (postgis) this FairDM is tested on. A portal uses the versions declared by the FairDM it pins, and moves its image and database when it moves FairDM. FairDM’s own test and image workflows read the PostGIS tag from the same table. See How to deploy a portal in a container and ADR 0036.

  • Base images for building a portal’s production container. docker/Dockerfile builds a runtime image (Python 3.13, uv, the PostgreSQL client library, GDAL, GEOS and PROJ, and a non-root user) and a development image (the same, plus git and build tools). Neither contains FairDM: a portal installs its locked dependencies on the development image and copies them onto the runtime image, as docker/portal.Dockerfile shows. A container’s default command applies migrations, collects static files, then serves with gunicorn, and stops at the first step that fails. PORT changes the port, and the command worker starts a Celery worker instead. Executable files in /docker-entrypoint.d/ run as start steps after collectstatic and before the server, in name order. docker/smoke-test.sh checks the images and a portal built on them, on every pull request, and the test suite runs inside the development image. The images have a version of their own: the Image Release workflow, run from the Actions tab, publishes ghcr.io/fair-dm/fairdm:<version> and ghcr.io/fair-dm/fairdm:<version>-dev and never moves a tag it has published. See How to deploy a portal in a container.

  • The docker-compose.yml development stack works again. It builds the development image, mounts the checkout, and starts PostGIS, Redis, the development server and a Celery worker with docker compose up. compose/django/Dockerfile is gone. The deployment guide shows a portal’s own compose file on the same image.

  • Search fields for records, people and organizations. A form or filter that chooses a project, dataset, sample, measurement, person or organization now searches on the server and loads twenty results at a time, so a portal with 100,000 samples answers a sample search with its first page in under a second. Each field offers only what the person using it may reach, refuses any other value when the form is saved, and keeps a stored link to a record the person cannot see as a private record without its name. Samples are found by name, local ID and identifier, people by name and ORCID, organizations by name and ROR identifier, and an identifier typed exactly is listed first. The fields take scope, depends_on, prefer, owner and type, and list filters, the project list’s tag filter, the publication, tag and ROR lookups and the forms and filters FairDM generates for registered types use them. Each address limits a caller with four new request limits, autocomplete_anon_burst, autocomplete_anon_day, autocomplete_user_burst and autocomplete_user_day. python manage.py seed_record_search seeds a walkthrough in development, and --large adds 100,000 samples. See How to add a record field to a form, Record fields and Limits on the API.

Changed#

  • FairDM requires django-mvp 0.30, django-mvp-forms 0.7, django-mvp-accounts 0.4 and django-mvp-compliance 0.3. List and table pages show the filters that are not in the toolbar in a panel beside the results, in place of the Filter dialog. On narrower screens the panel is a drawer opened by the Filters button. The results update in place when a filter, the sort or the page changes. The facts column on project, dataset, sample, measurement, person and organization pages is now django-mvp’s side panel, headed “At a glance”. It sticks under the header from the xl breakpoint and now stacks below xl after the content, where it stacked below lg before. Alerts show their icons again. A number field with a unit is drawn as one joined control.

    Upgrading a portal:

    • A template that overrides overview.side keeps working. One that copied the old grid markup from overview/page.html should fill page.side instead.

    • A portal that set --mvp-compliance-header-clearance can delete that rule. django-mvp-compliance 0.3 removed it and follows --mvp-header-height.

    • A list template that overrides page.toolbar or page.panel should read the “The filter panel” section of django-mvp’s documentation.

  • Breaking: FairDM runs on Django 6.0. The Django requirement is >=6.0,<7.0, so a portal moves to Django 6.0 when it moves to this FairDM. Django 5.2 is no longer supported. django.contrib.postgres is now in FairDM’s installed apps: Django 6.0 refuses to migrate a database whose models use a PostgreSQL index without it, and every location field has one.

  • The development accounts are at example.com. create_dev_accounts now creates portal.administrator@example.com, data.curator@example.com, community.manager@example.com, portal.developer@example.com and regular.user@example.com, matching the accounts the demo seeds create. regular.user@example.com is the account seed_overviews already makes, so the commands share it. Accounts an earlier run left at fairdm.org stay in a development database, and fairdm.E501 no longer looks for them: delete them, or start from a fresh database. See Development accounts.

  • Breaking: a list view takes its search and sort from its filterset. FairDM requires django-mvp 0.29 and django-mvp-forms 0.6. A view that subclasses FairDMListView or FairDMTableView and declares search_fields, max_search_words or order_by, or that composes django-filter’s FilterView, raises ImproperlyConfigured when its module is imported. Declare mvp.filters.SearchFilter and mvp.filters.SortFilter on the view’s filterset instead, and name the fields drawn in the toolbar in toolbar_filters. The project, dataset, people and organisation lists follow this: the search is q and the sort is o, as django-mvp names them, and the sort keys are unchanged. The toolbar holds the search and the status on projects (a multiple choice, so several statuses can be selected at once), the search and the licence on datasets, the search, the active and the staff switches on people, the search and the country on organisations, and the search and the status on every sample and measurement listing that has them. Every other filter sits in the Filter dialog. A registered type’s search_fields still names its searched fields, and the generated filterset carries a q filter over them. A configuration that overrides get_filterset_class() and builds the set with FilterFactory passes search_fields=self.get_search_fields(). See How to move a list view’s search and sort into its filterset.

  • Range filters on registered types use a pair of range inputs. Number and date range filters in a generated filterset draw django-mvp-forms’ RangeInput, DateRangeInput and DateTimeRangeInput. Their query parameters are <field>_0 and <field>_1, where they were <field>_min and <field>_max (numbers) or <field>_after and <field>_before (dates).

  • Image fields use django-mvp-forms’ ImageInput. The project, dataset, sample, measurement, person and organisation forms show the stored image and the newly chosen one, in place of easy-thumbnails’ clearable input. The thumbnail is larger and opens the file picker itself; a person’s image is drawn as a circle.

  • The sample and measurement filter sets search on q. The search in SampleFilter and MeasurementFilterMixin is now the q parameter, a mvp.filters.SearchFilter, where it was search. A listing draws it as the one search box in its toolbar, and a filter set built on either class no longer shows a second search field in the Filter dialog.

Removed#

  • django-compressor and django-libsass are no longer dependencies. No template in FairDM used {% compress %}, so the compress step could only fail, and the container start sequence no longer runs it. FairDM drops the compressor app, the CompressorFinder static finder, every COMPRESS_* setting and the compress step of the production setup sequence. A portal that uses {% compress %} or django_libsass adds django-compressor (and django-libsass) to its own dependencies, adds compressor to its INSTALLED_APPS, adds compressor.finders.CompressorFinder to STATICFILES_FINDERS, sets its own COMPRESS_* settings, and runs python manage.py compress before it serves.

    Upgrading:

    1. Remove the compress step from your own start command. A container or deployment script that runs python manage.py compress stops with Unknown command: 'compress'. If you build on FairDM’s base images, their start sequence no longer runs it.

    2. Search your templates for {% load compress %} and {% compress %}. If you find none, you are done. If you find them, add django-compressor (and django-libsass if you compile SCSS) to your portal’s dependencies, add "compressor" to INSTALLED_APPS and "compressor.finders.CompressorFinder" to STATICFILES_FINDERS, set the COMPRESS_* settings your templates rely on, and run python manage.py compress before the server starts, as a start step when you build on the base images.

  • fairdm.utils is no longer an installed app. It was registered with the label utils only to serve its templates and static files. Those now live in fairdm/templates/ and fairdm/static/ at the same paths, so templates and static files resolve as before. fairdm.utils stays importable as a plain package of helpers. Code that looked up the utils app config (apps.get_app_config("utils")) no longer finds it.

  • Breaking: django-autocomplete-light, django-select2 and django-addanother are no longer dependencies. FairDM’s search boxes are built on django-tomselect, which replaces all three. The dal, dal_select2, django_select2 and django_addanother apps, the autocomplete/ and select2/ addresses, the autocomplete:concept, autocomplete:contributor and autocomplete:organization address names, the select2 cache and the SELECT2_* settings are gone. ConceptSelect, ConceptMultiSelect, ContributorSelect2Widget, PersonSelect2Widget, OrganizationSelect2Widget, SelectizeWidget and CreatorsFormField are removed, and FieldInspector.suggest_widget answers Select and SelectMultiple for a relation. The admin pages for people and datasets use Django’s own autocomplete_fields.

    To move a portal:

    1. Search the portal for dal, django_select2, django_addanother, ConceptSelect, ConceptMultiSelect, SelectizeWidget, CreatorsFormField, PersonSelect2Widget, OrganizationSelect2Widget and ContributorSelect2Widget.

    2. Replace a field that chooses a project, dataset, sample or measurement with ProjectChoiceField, DatasetChoiceField, SampleChoiceField or MeasurementChoiceField from fairdm.contrib.autocomplete.fields, or the matching ...MultipleChoiceField. Pass scope="edit" where the form places a record inside another. Replace a person or organization field with PersonChoiceField or OrganizationChoiceField. A ModelSelect2Widget with search_fields becomes the field of that kind, and the search lookups are the field’s own.

    3. Replace a vocabulary field built with ConceptSelect or ConceptMultiSelect with mvp_forms.widgets.TomSelectMultiple(counted=True) on a model choice field of the vocabulary’s concepts, or with a plain select for a short list.

    4. Replace SelectizeWidget and CreatorsFormField with a model multiple choice field and TomSelectMultiple, and keep the Creator role logic in the form’s save().

    5. Replace an admin’s formfield_overrides that names a Select2 widget with autocomplete_fields, and give each target admin search_fields.

    6. Delete the routes select2/ and autocomplete/ from the portal’s URL conf if it includes them, and the select2 entry of CACHES and the SELECT2_* settings.

    7. If the portal still imports one of the three packages for its own code, add it to the portal’s own dependencies and INSTALLED_APPS. django-select2 stays installed because django-mvp depends on it, but FairDM no longer adds it to INSTALLED_APPS.

    8. Run python manage.py check and the portal’s tests.

Fixed#

  • Quantity fields can be edited. A quantity field’s form field was a plain number input, which dropped the stored value (it carries its units), so every quantity box on an edit page was empty and saving the page unchanged failed with “Enter a number.” A quantity field is now edited as a number with a unit list, using django-pint’s form fields, and an edit form shows the stored value in the field’s base units with that unit selected. A value entered in another unit from unit_choices is stored converted to the base units. See Special fields.

[v0.1.0] - 2026-10-16#

Added#

  • A location on every sample and measurement, typed as decimal degrees in WGS 84. A sample and a measurement have location (a point in WGS 84), location_elevation (metres above mean sea level) and location_uncertainty (metres), all optional and all their own: two samples at the same coordinates share nothing. The database refuses an elevation or an uncertainty without a point, and a negative uncertainty. A sample type shows the location input in its form when its registration lists location in its fields. The input takes latitude and longitude as signed decimal degrees, from -90 to 90 and from -180 to 180. Every coordinate is entered in WGS 84, with no reference-system input and no degrees, minutes and seconds, so a researcher whose notebook uses another system or notation converts it first; other systems are tracked in #512 and other notations in #513. fairdm.utils.location.forms has LocationField, LocationWidget and LocationFormMixin. A sample’s page shows its elevation and uncertainty with its latitude and longitude to five decimal places, and c-card.location takes elevation and uncertainty. An organization has a location point of its own. Run migrate when upgrading. See Locations.

    Upgrading. Existing locations are not carried across, so follow these steps in order:

    1. Rename a field of your own that clashes. A sample type or a measurement type that declares a field called location, location_elevation or location_uncertainty fails to load once the upgrade is in place. A location text field or foreign key on a measurement type is the usual case. Rename the field, and move its data with a migration of your own, before you upgrade.

    2. Search your code and templates for what read the old record, and change each hit:

      • location.latitude and location.longitude read location.y and location.x. A template that still writes {{ sample.location.latitude }} renders nothing, with no error.

      • Filters on location__x, location__y and location__crs no longer apply. Use inside, within_distance and nearest, or filter on location itself.

      • select_related("location"), prefetch_related("location"), autocomplete_fields or raw_id_fields listing location, and a form or admin that lists location for a person, raise when they run or when Django checks them.

      • PointFactory is removed. Give a sample factory location=Point(longitude, latitude, srid=4326).

      • Links to /location/<lon>/<lat>/ and Dataset.bbox are gone. Use Dataset.spatial_coverage(user).

      • Remove FAIRDM_CRS, FAIRDM_X_COORD and FAIRDM_Y_COORD from your settings.

    3. Export the coordinates you need to keep. The migrations drop the table behind Point and do not copy its rows to the samples.

    4. Run migrate, then enter the locations again. A sample’s form takes them when its registration lists location in its fields, and an import file takes them in latitude and longitude columns, with the optional location_elevation and location_uncertainty.

    5. Check your registrations. A sample type or a measurement type shows the location input only when its fields list location. A type that listed no fields shows it already.

  • A measurement can record where it was made. A measurement type shows the location input in its form when its registration lists location, and the measurement’s page maps its own location and says it is the measurement’s. A measurement with none of its own is where its sample is, but only for a viewer who may open the sample. Measurement.effective_location_for(user) and MeasurementQuerySet.with_effective_location(user) give that location, and the page’s context carries it as effective_location. See Locations.

  • Find samples, measurements and organizations by where they are. inside(area) takes a polygon or a (west, south, east, north) tuple and counts a point on the edge as inside. within_distance(point, distance) takes a D or metres and measures on the ground, and nearest(point) orders nearest first and carries distance. Each reads a spatial index and combines with visible_to(). A measurement’s lookups take the viewer and find it by its own location, else its sample’s for a viewer who may open the sample. See Locations.

  • The spatial coverage of a dataset and of a project. Dataset.spatial_coverage(user=None) and Project.spatial_coverage(user=None) return the smallest box holding the locations the viewer may open, measurements included, or None when nothing is located. Locations on both sides of the 180th meridian give a narrow box with its western bound east of its eastern one. The collection tables’ Latitude and Longitude for a measurement are its effective location for the viewer. See Locations.

  • The API returns a record’s location as a GeoJSON point. A sample and a measurement return location, a Point in WGS 84 with longitude first and the elevation as a third coordinate where one is recorded, and location_uncertainty in metres beside it. An organization returns location without an elevation, and a person returns none. A record with no location returns null, and a measurement returns only its own location, never its sample’s. The three location fields are read-only. See A record’s location.

  • A location is four columns in tabular import and export. Where a sample or measurement type’s fields or resource_fields list location, its resource has latitude, longitude, location_elevation and location_uncertainty in place of one. Export writes the record’s own values in WGS 84 decimal degrees, and a measurement never writes its sample’s location. Import reads the coordinates as decimal degrees, with the location input’s ranges, and reports a row it refuses instead of saving it. See Locations.

  • An organization’s point is typed on its forms. The organization’s profile page, the form that adds an organization and the older profile form take a latitude and a longitude as decimal degrees in WGS 84, in place of the map input. An organization added from ROR still takes the coordinates ROR publishes, and a person placed on a map is placed at their primary affiliation’s organization’s point. See Locations.

  • A template tag that asks whether the viewer holds a level on a record. {% holds_level "edit" object as can_edit %}, from plugin_tags, answers for the view, edit or manage level on a project, dataset, sample or measurement, decided as the record’s own pages decide it. A template that fills a block of a record’s page can guard what it adds without a view of its own. plugins.holds_level(request, level, record) asks the same from Python. See Create a plugin.

  • A landing page for visitors who have not signed in. The address / now opens on a full-height hero and follows it with public figures, the portal’s description, the latest datasets, the registered sample and measurement types, the community, new projects, the API, an invitation to join and a footer. Everything shown is what a visitor may open, and a section with nothing to show is left out. HOME_PAGE_CONFIG sets the hero’s eyebrow, title, lead, image and logo. Each section sits in a landing.<name> template block and is a c-landing.* component, and FairDMHomeView reads each section’s data from a get_* method a subclass can override. Creating an organization from a ROR ID raised decimal.InvalidOperation for every ID, and the sync saved no place at all. Both now request https://api.ror.org/v2/ and read the display name, the aliases and acronyms, the links and the first location from the version 2 record. The sync also writes to the organization itself, where before its city never reached the saved organization. In the API, the name_identifier and scheme_uri of a Wikidata or Crossref Funder ID identifier now carry its address. Changed#

  • FairDM is released on GitHub, and a portal pins it to a release tag. A merged release pull request creates the tag and the GitHub release. FairDM is not published to PyPI, because django-literature and django-research-vocabs are installed from git. A portal installs FairDM with a git source pinned to a tag, for example fairdm = { git = "https://github.com/FAIR-DM/fairdm", tag = "v0.1.0" } under [tool.uv.sources], rather than to a commit.

  • FairDM runs on PostgreSQL with the PostGIS extension, and installs GeoDjango. The database engine is django.contrib.gis.db.backends.postgis in every environment, whatever scheme DATABASE_URL uses, and django.contrib.gis is an installed app. There is no setting to run on plain PostgreSQL. A portal’s database needs the PostGIS extension, and its server or image needs the GDAL, GEOS and PROJ libraries. The development module no longer uses SQLite: development reads DATABASE_URL or the POSTGRES_* variables like every other environment. fairdm.E101 now refuses any engine other than PostGIS, where it refused SQLite before. docker-compose.yml starts PostGIS, Redis, a Celery worker and the development server, and the test suite runs against PostGIS locally and in CI. See The technology stack and Configuration checks.

  • The sign-in, sign-up and other entrance pages are laid out in two halves. The form takes one half of the window. The other names the portal, gives its description and says who runs it, on a background in the theme’s colours. Below 1024 pixels the form has the page. These pages drew one centred card before. A portal replaces the pane with a cotton/entrance/aside.html of its own, and the whole layout with mvp_accounts/entrance/base.html. See Entrance pages.

  • The django-mvp packages move to their latest releases. django-mvp 0.28.2, django-mvp-forms 0.4.0, django-mvp-accounts 0.3.0, django-mvp-charts 0.3.0 and daisy-cotton-ext 0.5.0. Nothing in FairDM’s own code or templates needed changing. What a portal will notice:

    • The sign-in and sign-up pages are arranged differently, and show the portal’s logo above the card. The passkey, emailed-code and ORCID buttons sit together, apart from the form, and the link to the other page is at the foot of the card. A portal that replaced allauth/layouts/entrance.html to change the frame around these pages moves that to mvp_accounts/entrance/base.html. See django-mvp-accounts’ 0.3.0.

    • Long help text and long checkbox labels on a form wrap on a narrow screen, where they used to push the form wider than the screen.

  • Projects, datasets, samples and measurements have a database index on modified. The API’s modified_after and modified_before filters, and ordering a list by modified, can use it where they scanned the whole table before. Contributors already had the index. Each of the four apps gains one migration that creates it, so run migrate when upgrading (#466).

  • The REST API is complete, and a portal with API clients or serializers of its own has changes to make. See The REST API and Limits on the API. What to change:

    • Records refer to each other by short identifier, and no response carries a database number. The id field is gone from every record. project, dataset and sample are {"uuid", "url"} objects, or null when the caller may not see the record, where they were numbers. A request names a parent by its short identifier, as a bare string or as that object, and a database number is refused. A serializer of your own declares each relation it adds as a fairdm.api.serializers.RecordReferenceField or a StringRelatedField.

    • A relation filter matches on the short identifier. ?dataset=, ?sample= and a type’s filters on a project or a contributor take the related record’s short identifier and refuse a database number. A filter on a relation whose model has no short identifier, such as a content type, is not offered. Every sample list takes ?dataset= and every measurement list also takes ?sample=.

    • Every sample and measurement carries the common fields, whatever its registration lists: url, html_url, uuid, name, dataset, added and modified, and local_id and status for a sample and sample for a measurement, then the metadata (descriptions, dates, identifiers, keywords, contributors). The fields a type declares come after them, and a measurement’s measured values are included.

    • Tokens come from the account pages, and the password login is gone. A person creates a token at /account/tokens/, shown once and revocable, and a script sends it as Authorization: Token <token>. The addresses under /api/v1/auth/, which exchanged a password for a token and managed accounts, no longer exist, and dj-rest-auth and djangorestframework-guardian are no longer dependencies. The tokens are kept by django-rest-knox, which FairDM installs and configures through REST_KNOX. Existing Django REST framework tokens stop working, so scripts need new ones. A portal that listed dj_rest_auth or rest_framework.authtoken in its settings removes them.

    • A serializer of your own builds on the base, and a registration is checked at start-up. A serializer for a sample type must subclass BaseSampleSerializer and one for a measurement type BaseMeasurementSerializer, however it is supplied (serializer_class or an overridden get_serializer_class). Otherwise the portal refuses to load its API routes with ImproperlyConfigured. Core measurements (Feature 006)#

  • A measurement type may nominate a value and, where the analysis produces one, an uncertainty, and gets formatted reporting for free. get_value() and print_value() read those two fields and require nothing else from the type — no method to override, no string to build by hand. ICP_MS_Measurement ships with both fields as the worked example.

  • The quantity formatter is installed when the application starts, not the first time a template loads it. A value read or rendered outside a template — in a shell, a management command, a test, an API response built without a template — now formats the same way a page does; previously it fell back to the unit library’s own default formatting until some template happened to import the tag module that installed it.

  • The measurement type filter offers every registered type, not a fixed pair of applications. It previously drew its choices from two hardcoded application labels, so the measurement record’s own type was absent from the list, every unrelated model in those two applications appeared, and a portal’s own measurement types — which live in the portal’s own application — could never be selected. It now asks the registry, the same source the administrative interface already used.

  • Date filtering accepts a year, a year and month, or a full date, matching what a measurement’s own date fields accept. Filtering by an out-of-range or malformed date now reports a form error instead of an unhandled exception when the filtered list is rendered.

  • The registry validates a measurement type’s administrative class against the class portals were already told to inherit from. It previously validated against, and generated for a type supplying none, an unconfigured two-line stand-in — so a measurement type that inherited from the documented base as instructed was refused at registration, and one that supplied no administrative class of its own received none of the framework’s inline editors, autocomplete fields or read-only handling. See Removed, below, for the stand-in’s deletion.

That wiring previously existed for specimens and not for measurements, so it reached only the portals that wrote their own form and filter classes — the group that needed it least.

  • Rights over a dataset reach its measurements. A user holding view, change or delete over a dataset holds the matching right over the measurements in it; a right granted directly on a registered measurement type is honoured the same way.

  • Two form defects are fixed: the “add another dataset” control on a measurement form previously pointed at an administrative address that does not exist, and the form’s field guidance text (name, dataset, sample, tags) was declared under the wrong attribute and never reached the rendered form. Both mirror fixes already made on the equivalent sample form.

  • Creating a bare Measurement — the polymorphic base every measurement type inherits from — is refused everywhere a bare Sample already is, including the framework’s own test fixtures, which previously built one directly.

  • Measurement.objects offers with_related() and with_metadata(), chainable with each other and with ordinary queryset methods, so a list of measurements loads its sample, dataset, contributors, descriptions, dates and identifiers in a number of queries that does not grow with how many measurements there are.

Contributors and Contributions (Feature 009)#

  • fairdm.contrib.contributors, a new app holding every contributor record. Contributor is a polymorphic base with two concrete types: Person — the account a user logs in with (AUTH_USER_MODEL = "contributors.Person") — and Organization. Both share a public identifier (uuid, prefixed c), a name, alternative names, a profile, a profile image, links, language preferences, a location and a general-purpose config JSON store.

  • Affiliation (aliased OrganizationMember) links a Person to an Organization with a membership type (PENDING, MEMBER, ADMIN, OWNER), a primary flag and partial-precision start/end dates. A person cannot hold two affiliations with the same organisation, and at most one of a person’s affiliations is primary at a time — both enforced by validation and by a database constraint.

  • Contribution credits a contributor on a Project, Dataset, Sample or Measurement through a GenericForeignKey, carrying roles drawn from the framework’s fairdm-roles vocabulary. Crediting the same contributor again under a further role accumulates the role on the existing credit rather than replacing it (Contributor.add_to(), the Contribution.add_to() classmethod).

  • ContributorIdentifier holds a contributor’s external identifiers (ORCID for a person, ROR and others for an organisation), each syncing in the background on creation.

  • Organization.type, drawn from ROR schema 2.1’s institution types (OrganizationType): education, funder, healthcare, company, archive, nonprofit, government, facility, other.

  • Derived account state. Person.account_state (AccountState: GHOST, INVITED, CLAIMED, INACTIVE) is computed from is_active, is_claimed and email rather than stored, and Person.objects carries a matching queryset method for each state — ghost(), invited(), claimed(), inactive() — plus real() (excludes superusers and the django-guardian anonymous placeholder) and unclaimed().

  • Derived organisation ownership. manage_organization is not a stored permission — OrganizationPermissionBackend answers it from whether the user holds an OWNER affiliation on the organisation at the moment of the check. Organization.transfer_ownership() demotes the incumbent owner to ADMIN and promotes the named member to OWNER in one atomic operation.

  • ClaimingAuditLog, an immutable record of every profile-claiming event (method, source and target person, success, failure reason), with ClaimingAuditLogManager filters — for_person(), failures(), by_method(), recent().

  • Reporting methods on Contributor: projects, datasets, samples, measurements, get_credit_counts(), get_collaborators(), has_contribution_to(), get_recent_contributions(), get_contributions_by_type().

  • Export helpers Contributor.to_datacite() and .to_schema_org(), backed by DataCiteTransform, SchemaOrgTransform, CSLJSONTransform, ORCIDTransform and RORTransform (fairdm.contrib.contributors.utils.transforms) — each a transform instance with export()/import_data() methods.

Changed#

Core samples (Feature 005) — breaking#

  • fairdm.factories.SampleFactory is abstract. It declares the fields every specimen shares but can no longer be instantiated directly, matching Sample itself. A portal (or test) that called SampleFactory() now subclasses it — fairdm_demo.factories.RockSampleFactory is the reference example — the same way a portal already subclasses Sample for its own specimen types. MeasurementFactory.sample and SampleRelationFactory.source/target have no default for the same reason and must be passed a concrete specimen instance.

  • A sample’s status describes where the specimen physically is. The previous vocabulary was fetched over plain HTTP from a third-party host while Django loaded its applications, and its terms — complete, ongoing, planned, unknown — describe a data-collection activity rather than a specimen. It is replaced by a local vocabulary of custody states: available, in use, stored, destroyed, unknown. Every existing status value is rewritten to unknown, because none of the previous terms maps onto a custody state; the previous values are discarded and cannot be recovered. A portal that read a sample’s status will find it reset.

  • The sample identifier vocabulary is narrowed to IGSN and DOI. A portal storing any other type against a specimen will find it refused by validation.

  • An IGSN is validated as a DataCite identifier, not against the legacy handle prefix. IGSN allocation moved to DataCite in 2023 and identifiers are now spread across dozens of registry prefixes, so the previous pattern rejected essentially every identifier in circulation. The legacy handle form is still accepted.

  • An identifier value is unique across every record type, not merely within one. The uniqueness was declared on a shared abstract, which gives one index per table, so the same value could name a specimen and a dataset at once. Projects and measurements inherit the check too.

  • A sample’s descriptions, keywords, key dates and edit pages require the right to change it. They previously opened for anyone holding the specimen’s address, including a visitor who had not signed in.

  • Object-level permissions resolve for a portal-defined specimen type. The right is declared on the base record and the specimen lives in the portal’s own application, so the check raised and the grant looked for a permission filed under the wrong content type. A shared backend normalises the record before the check, and fairdm.core.utils.assign_perm does the same when granting. Measurements gain the same repair. guardian.backends.ObjectPermissionBackend is no longer in AUTHENTICATION_BACKENDS; fairdm.core.permissions.PolymorphicObjectPermissionBackend replaces it and a portal listing the backends by hand should follow.

  • The specimen hierarchy has one traversal. The queryset’s ancestor and descendant walks ran opposite to the record’s own, so each returned what the other promised. Neither had a caller.

  • A specimen cannot be its own parent, and two specimens cannot each descend from the other, when saved directly rather than only under validation.

Upgrading a portal that holds samples:

  1. Export the sample statuses before you migrate if you need a record of them. Migration sample.0008_migrate_sample_status_to_unknown rewrites every sample’s status to unknown and does not reverse. For example:

    import csv
from fairdm.core.sample.models import Sample

with open("sample_status_backup.csv", "w", newline="") as f:
    writer = csv.writer(f)
    writer.writerow(["uuid", "name", "status"])
    for sample in Sample.objects.values_list("uuid", "name", "status"):
        writer.writerow(sample)

  2. Update your own code, filters and reports that compare sample.status with "complete", "ongoing", "planned" or "available" as a form default. The valid values are now available, in_use, stored, destroyed and unknown.

  3. Write a concrete factory for each of your own sample types, subclassing fairdm.factories.SampleFactory, and replace every SampleFactory(...) call in your tests:

    from fairdm.factories import SampleFactory
from myapp.models import RockSample

class RockSampleFactory(SampleFactory):
    class Meta:
        model = RockSample

    Pass a concrete sample wherever you relied on a default, for example MeasurementFactory(sample=RockSampleFactory()).

  4. Retarget any code that creates a bare Sample. Creating one through Sample.objects.create(), .save(), a form, the admin or fixture loading raises ValidationError. Search for Sample.objects.create(, for Sample( followed by .save(), and for fixtures with "model": "sample.sample", and point each at a concrete sample type.

  5. Check sample identifiers. The type vocabulary is now exactly IGSN and DOI. Django does not validate choices on save, so a row can hold a stale type that fails full_clean(). Find them with SampleIdentifier.objects.exclude(type__in=SampleIdentifier.VOCABULARY.values) and retype or delete each. A local lab barcode belongs in the sample’s local_id.

  6. Expect two changes to every identifier value. A display prefix such as https://doi.org/, http://doi.org/, https://igsn.org/, hdl.handle.net/, doi: or igsn: is stripped before the value is compared or stored, and a value must be unique across projects, datasets, samples and measurements. If your code validates IGSNs against ^10273/[A-Z0-9]{9,}$, remove that pattern: an IGSN now validates as any DataCite DOI or the legacy 10273/ handle.

  7. Replace direct calls to guardian.shortcuts.assign_perm, remove_perm, get_perms or get_objects_for_user against a sample, a measurement, an organization or a person with the function of the same name in fairdm.core.utils. Calls against a non-polymorphic model are unaffected. If your settings list AUTHENTICATION_BACKENDS by hand, replace guardian.backends.ObjectPermissionBackend with fairdm.core.permissions.PolymorphicObjectPermissionBackend.

  8. Check any view, template or link of your own that assumed the sample editing pages were open without a permission. They now require sample.change_sample. Give the people who should keep access the edit level on the sample or on its dataset, on the Contributors tab.

Portal configuration (Feature 001) — breaking#

  • fairdm.setup() no longer accepts settings as keyword arguments. The **overrides parameter is gone; assign the setting after the call instead, which was already the documented pattern and is now the only one. A portal passing settings this way will raise TypeError until it moves them.

  • DJANGO_SECRET_KEY and DJANGO_SITE_DOMAIN no longer have working defaults. FairDM previously shipped a fallback secret key in its own source, so a production portal that never set the variable started on a key anyone could read and had its sessions and signed cookies forgeable. Both variables now hold an unusable value until set, and the production checks refuse the boot. Development is unaffected — the development override supplies clearly-marked local values.

  • Portal apps are registered ahead of FairDM’s in INSTALLED_APPS, so a portal’s own templates and static files now take precedence over FairDM’s at the same path. A portal that already ships a shadowing template will find it served where it was previously inert.

  • The staging environment is no longer supported. fairdm/conf/staging.py is deleted and DJANGO_ENV=staging now resolves to the production baseline. A portal that wants staging supplies its own staging.py beside its settings module, which applies through the same layering as any other environment. Because those settings are the production baseline, a staging boot is held to the production-critical checks.

  • THUMBNAIL_DEBUG is off in the baseline. easy-thumbnails re-raises rather than degrading to a blank image when it is on, which turned a missing source file into a 500. It is on in development, as before.

Core datasets (Feature 004)#

  • Datasets are private by default. Reading datasets the ordinary way no longer returns private ones. Dataset.all_objects is the explicit route for code that needs them, and the surfaces whose own permission check is the real gate — the API, plugin pages, the sample and measurement forms, and the administrative interface — use it so that check still runs.

  • Dataset identifiers use a vocabulary that applies to datasets. The type list previously offered identifiers for people and organisations.

  • Datasets are ordered most-recently-modified first. The previous ordering put the least recently touched record first.

  • A dataset created without choosing a licence carries the portal’s configured default, and the licences the framework recommends are seeded when a portal is stood up. A portal that has migrated previously had no licence rows at all, which left the default silently unapplied.

  • A dataset’s descriptions, keywords and key dates now require the change_dataset permission. These pages previously opened for anyone holding the dataset’s address, including an unauthenticated visitor, and a portal upgrading will find that contributors who were never granted object-level rights over a dataset can no longer reach them.

  • Creating a dataset through the portal grants the creator rights over it, matching what creating a project has always done. Without it a new dataset was unreachable by the person who had just made it, because a dataset is private by default.

  • A dataset a user may not see answers 404 rather than 403, so a page no longer confirms that a private dataset exists.

Contributors and Contributions (Feature 009)#

Using New Introspection Features#

from fairdm.registry import registry

# Iterate over all registered Sample models
for sample_model in registry.samples:
    print(f"Sample: {sample_model.__name__}")

# Access all registered Measurement models
