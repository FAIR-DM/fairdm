Plugins#

This page lists everything the plugin framework gives you: the registration decorator, the Plugin base class, the registry, the helper functions and the errors a refused registration raises. It does not show how to build a plugin, which is in How to create a plugin, or how access to a record is decided, which is in How access to a record is decided.

A plugin is a Django view attached to a core record type. Registering it gives the view an address under the record, an entry in the record’s tab navigation, and the record itself as base_object.

Import from fairdm.plugins, which re-exports fairdm.contrib.plugins:

from fairdm import plugins
from fairdm.plugins import Plugin

Addresses and URL names#

A plugin is mounted at <record prefix>/<url_path>/. An additional view is mounted at <record prefix>/<plugin url_path>/<view url_path>/.

URL names are flat, with no nested namespace:

View

URL name

The plugin

<name>

An additional view

<plugin name>-<view name>

The name of a view is its class name, slugified, unless it sets name. Notes becomes notes and NoteEdit becomes note-edit, so the additional view in Notes.extra_views is named notes-note-edit.

Names are unique for each record type, not across record types.

Mounting a record type#

A record type accepts plugins when a URL configuration mounts its patterns. FairDM does this for the five record types above. For another record type, include the patterns under the route the registry gives:

from django.urls import include, path

from fairdm.plugins import registry

urlpatterns = [
    path(
        f"stations/{registry.route_for(Station)}/",
        include((registry.get_urls_for_model(Station), "station")),
    ),
]

The namespace is the lowercase model name. get_urls_for_model also builds the record type’s navigation menu, so register the plugins before the URL configuration is imported.

A plugin’s tab is marked as the current page on every address the plugin mounts: its own, each additional view’s, and any extra pattern its get_urls adds.

Helper functions#

All are importable from fairdm.plugins.

is_instance_of#

is_instance_of(*model_classes)

Returns a check(request, obj) predicate. It passes when obj is an instance of one of model_classes, and when obj is None.

has_perm#

has_perm(request, permission, obj=None)

Returns True when the request’s user holds permission on obj, or for the whole model when obj is None. On a record, a model-wide permission counts only when it is held through a shipped portal role. The answer is remembered for the rest of the request.

holds_level#

holds_level(request, level, obj)

Returns True when the viewer holds level on a project, dataset, sample or measurement. level is "view", "edit" or "manage", standing for the view_<model>, change_<model> and delete_<model> permissions. Returns False when obj is None or is not one of those four, and for a visitor who is not signed in. Raises ValueError for any other level. The template tag of the same name is in Template tags. The levels are described in Contribution levels and record access.

can_open#

can_open(view_class, request, obj=None)

Returns True when the view’s check passes and every permission in its permission is held. Both the navigation entry and the page itself ask this one function. It reads only the check and permission of the class it is given. An additional view takes nothing from its plugin.

reverse#

reverse(instance, view_name, *args, **kwargs)

Returns the URL of a plugin view for a record. The namespace is the record’s type_of model when it has one, otherwise its own model, lowercased. Keywords named in the record type’s addressing are filled in from the record.

from fairdm.plugins import reverse

reverse(sample, "analysis")

slugify#

slugify(text)

Returns the slug a class name becomes. URLTestPlugin becomes url-test-plugin.

Mixins#

Both are in fairdm.contrib.plugins.mixins. List them before Plugin.

Mixin

What it does

PrivateRecordNotFoundMixin

Answers a refused request for a non-public record with a 404, so the address does not confirm the record exists. A refusal on a public record is the usual one. It reads visibility from the record, so it suits projects and datasets

RecordOwnPageBackFallbackMixin

On a deletion page, points Back at the record’s own page rather than its list. List it before the delete view

PluginRegistrationError#

fairdm.contrib.plugins.checks.PluginRegistrationError subclasses Django’s ImproperlyConfigured. Its message reads <plugin> registered against <model>: <problem>.

A registration is refused when:

  • no model is given, or a value is not a model class

  • check is neither a bool nor a callable

  • url_path is not a valid route

  • another plugin on the record type has the same name

  • another plugin on the record type has the same url_path

  • the URL names the plugin generates collide with another plugin’s

  • an extra_views entry is not a Plugin subclass

  • an extra_views entry is the plugin itself

  • an extra_views entry declares extra_views of its own

  • an extra_views entry has url_path = None

  • two extra_views entries claim the same segment

Samples and Measurements tabs#

fairdm.contrib.collections.plugins registers three plugins. Samples and Measurements subclass RecordsTab, a Plugin that is also a table view, and have the url_path values samples and measurements at orders 300 and 400. Each lists the samples or the measurements of the record whose page it is on, one registered type at a time. SampleMeasurements is a sample’s Measurements tab, described below.

Pages and records#

Page

Registered

Records the tab lists

Dataset

Yes

The samples or measurements of the dataset that the viewer may see

Project

Yes

The samples or measurements of any of the project’s datasets that the viewer may see

Contributor

Yes

The samples or measurements credited to the contributor, or beneath a dataset or project credited to them: the released ones, unless it is the person’s own page, where the viewer sees what they hold a level on as well. One registration covers Person and Organization

RecordsTab.scope() returns every record of the kind that belongs to the page’s record, and visible_records() narrows it with visible_to(viewer), where viewer() is the request’s user. holder names the kind of page, "dataset", "project" or "contributor", from the model the mount was registered for, and scope() follows it. A contributor’s scope is Contributor.get_associated_records(base_model), described in Contributor models. A page that gains the tabs registers the plugins for its model and extends scope(). A measurement belongs to its own dataset, which can differ from its sample’s dataset: a project’s Measurements tab lists a measurement made on a sample of another project, and that sample is not on the project’s Samples tab.

The check is records_are_offered, which hands a dataset to dataset_records_visible, beside dataset_is_visible in fairdm.core.dataset.plugins, and a project to project_is_visible. A dataset’s check holds when the dataset’s overview opens for the viewer and so do its records: the dataset is published and no private project hides it, or the viewer holds a level on the dataset or its project, or the portal-wide right to view datasets (dataset.view_dataset). For anyone else the tab is not offered and its address answers 404.

A contributor’s tabs are offered to everyone, as the contributor’s overview is. viewer() returns None on a contributor’s page, so only records released to everyone are listed, unless a person looks at their own page (is_own_page()). Then it returns that person, who also sees the records they hold a level on. An organization’s page always lists released records only, even for a member of a dataset’s team. An organization is never “the viewer”, so what it is credited on in a private dataset is not listed.

A project’s tabs are offered to anyone who may open the project, and a private project answers 404 to everyone else. What a project’s datasets hold is decided row by row, so a viewer who may see none of them gets the same "empty" page as a project with no records.

Types and the address#

type_counts(queryset) counts a queryset’s records per registered type, most numerous first, and returns a list of RecordType entries. Each carries the model, its registry configuration, the count the viewer may see and the slug that names it in the address. The tab lists the most numerous type unless the address names another:

Address

Lists

…/samples/

The most numerous sample type

…/samples/<slug>/

The type with that slug. It has the tab’s own URL name, reversed with a type argument, so the tab strip marks the tab there too. 404 when the type is not listed

Records of a type that is no longer registered are listed under one more entry, FallbackType, with the slug other. It carries SampleTable or MeasurementTable, SampleFilter or MeasurementFilter and the plural name of the base model, and is offered only when such records exist.

A tab with nothing to list builds no table and no filter set. Its table is NoRecords, which has no columns, and KindName stands in for the registry configuration so the page can still name the kind. The page answers 200 and record_state is "empty" in its context. The context also holds type_entries, one dict per listed type with its name, address and count, kind and holder.

Columns, filters and search#

The table is the one generated for the type’s registration, so the tab and the portal-wide listing of that type show the same columns. The filter set and the search come from the registration in the same way: ModelConfiguration.get_table_class() and get_filterset_class(), and the q filter that search_fields builds. The tab then changes four things:

  • The first columns are the record’s name and, on measurements, SampleColumn. It links a sample only where the viewer may open it and shows a dash otherwise, and it orders the samples the viewer may not open as one block after the named ones.

  • DatasetColumn names a record’s dataset and links it where the viewer may open it. A project’s and a contributor’s tabs add it right after the name, as dataset_name. A dataset’s own tab does not.

  • StableOrderData ends every ordering with the primary key, so a page never repeats a row.

  • Fifty rows are shown to a page.

The filter set’s choices are scoped as on the portal-wide listings, through PublishedChoicesMixin. RecordsTab.get_filterset() then changes two things on the filter set it builds:

  • On a dataset’s own tab the dataset filter is removed, since every row is in that dataset.

  • The dataset and sample filters of a registered type search records through the autocomplete. On a dataset’s and a project’s tabs they search at scope "view", the records the viewer may see. On a person’s own page they search that person’s records, and on every other contributor’s page the public ones.

The overviews#

The dataset’s and the project’s overviews count their records with visible_to, so their Samples and Measurements figures, which link to the tabs, always equal the tabs’ totals. A project’s Datasets figure counts the datasets the viewer may see, so a member of a private dataset counts it and a visitor does not. On a dataset whose records the viewer may not see, the figures, the composition and growth charts and the spatial coverage are left out of the page.

A sample’s Measurements tab#

SampleMeasurements is registered on Sample with the name and url_path measurements, at order 400, so its URL name is sample:measurements. It is a Plugin with django-tables2’s MultiTableMixin, and lists every measurement made on the sample that the viewer may see: Measurement.objects.filter(sample=...).visible_to(user). A measurement is listed or left out by its own dataset, whichever dataset that is.

get_tables() builds one table per type that type_counts() finds, most numerous first, with the fallback table last for types no longer registered. Each table is the type’s registered table, fed by type_rows(), the function RecordsTab uses for its rows, and wrapped in StableOrderData. Each leads with the name and DatasetColumn, and drops the sample and dataset columns and the columns in BOOKKEEPING_COLUMNS. Each table has the prefix <type slug>-, so it sorts and pages by its own query parameters, such as ?xrf-page=2, and its pager is drawn with c-mvp.page.list.footer and that table’s prefixed_page_field. Fifty rows are shown to a page. The tab has no filter set and no search.

Its check is the sample overview’s, so it opens for exactly the viewers the overview opens for, and anyone else gets 404. The context holds sections, one dict per listed type with its type (a RecordType) and its table. With no measurement the viewer may see it is empty and the tab says so. Its template is record_lists/sample_measurements.html.

The sample’s overview links its Measurements figure and the Measurements card’s See all to the tab. A measurement’s overview links its list of other measurements on the same sample to it, where the viewer may open the sample.

Development data#

RecordListSeed creates the data behind every state of the tabs. Run seed_record_lists, which Management commands describes.

Members tab#

fairdm.contrib.contributors.plugins.organisation registers OrganizationMembers against Contributor at order 50, right after the overview, with the url_path members and the URL name contributor:organization-members. Its check is is_instance_of(Organization), so the tab is offered on an organization’s page only, to everyone the overview opens for, and a person’s page has none. get_base_object() raises Http404 for a person, so a person’s members/ address answers 404 for every viewer, signed in or not.

It subclasses PersonListView from fairdm.contrib.contributors.views.person, so it draws the People page’s cards, search and filters. get_queryset() narrows the people to the organization’s current, verified members, the same people Organization.get_current_memberships() returns:

The order comes from an annotation, membership, holding the person’s membership type. The cards’ relations are prefetched, so the number of queries does not grow with the members listed. With no members the page answers 200 and its empty state says that nobody is affiliated.

Subclassing#

A plugin is an ordinary class. A package can ship a plugin without registering it, and a portal registers a subclass:

@plugins.register(Sample, label=_("Citations"), icon="quote", order=520)
class Citations(CitationsPlugin):
    pass
