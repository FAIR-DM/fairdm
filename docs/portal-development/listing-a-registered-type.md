# What Registering a Type Produces

Registering a sample or measurement type gives it a browsable listing page. You write the
configuration class and nothing else: no URL entry, no template, no menu entry.

```python
# myapp/config.py
import fairdm
from fairdm.core.sample.config import BaseSampleConfiguration

from .models import RockSample


@fairdm.register
class RockSampleConfig(BaseSampleConfiguration):
    model = RockSample
```

Restart the server and the portal has:

- **A page** for the type, at `collections/samples/<model_name>/` (or
  `collections/measurements/<model_name>/` for a measurement), under the URL name
  `<model_name>-list`
- **Columns**, taken from the model's own fields when the configuration declares none
- **Filters**, one per field the listing presents, generated by django-filter
- **A search box**, matching a case-insensitive substring against the record's `name`
- **Column sorting**, on every column the table presents as sortable
- **A navigation entry**, under **Samples** or **Measurements** in the main menu
- **A switcher** on the page itself, offering every other registered type's listing

## What a listing shows

A listing shows every record of its type held anywhere in the portal whose dataset is published,
and nothing else. Publication is a single boolean on the dataset, set by an administrator in the
Django admin. It is independent of the dataset's metadata visibility: a private dataset that is
published contributes its records to the listings, and its rows carry the dataset's name without a
link to a page the reader would be refused.

Every viewer sees the same rows. There is no signed-in view of a listing and no per-record
permission check.

## Overriding one piece without taking over the rest

The registry produces six components (form, table, filterset, serializer, resource, admin) and
each one is reached through its own accessor, so replacing one leaves the other five generated.
There are three ways to do it, in increasing order of effort.

### Declare a field list

`fields` sets the fields every component uses:

```python
@fairdm.register
class RockSampleConfig(BaseSampleConfiguration):
    model = RockSample
    fields = ["name", "rock_type", "collection_date", "weight_grams"]
```

A per-component list overrides `fields` for that component alone. Here the table shows four
columns while the form, the API and the rest still use all of `fields`:

```python
@fairdm.register
class RockSampleConfig(BaseSampleConfiguration):
    model = RockSample
    fields = ["name", "rock_type", "collection_date", "weight_grams", "notes"]
    table_fields = ["name", "rock_type", "collection_date", "weight_grams"]
```

The same applies to `form_fields`, `filterset_fields`, `serializer_fields`, `resource_fields` and
`admin_list_display`.

One thing the table does on its own: it drops fields whose values are too long to sit in a cell.
A `TextField`, or a `CharField` with a `max_length` above 200, is left out of the generated table
even when you name it in `fields`, so that one long value cannot push every other column off the
page. The field still reaches the form, the API and the rest. If you want it in the table, supply
your own table class and add the column yourself.

### Supply your own class

When a field list cannot say what you need, subclass the matching base and name it. The base
tables live in `fairdm.contrib.collections.tables`: `SampleTable` for a sample type,
`MeasurementTable` for a measurement type.

```python
from fairdm.contrib.collections.tables import SampleTable


class RockSampleTable(SampleTable):
    class Meta:
        model = RockSample
        fields = ["id", "dataset", "name", "rock_type", "mineral_content"]

    def render_rock_type(self, value):
        return value.upper()


@fairdm.register
class RockSampleConfig(BaseSampleConfiguration):
    model = RockSample
    table_class = RockSampleTable
```

Declaring both a component's field list and its class is refused at registration, following
Django's own rule for `fields` and `form_class`. Use one or the other.

### Override the accessor

When the class itself has to be built at run time, override the accessor:

```python
@fairdm.register
class RockSampleConfig(BaseSampleConfiguration):
    model = RockSample

    def get_table_class(self):
        return build_table_for(self.model)
```

Every caller inside the framework reaches the table through `get_table_class()`, so an override
here is what the whole framework receives.

## Search, and the field you add

Search matches a case-insensitive substring against the fields `search_fields` names. Declaring
nothing searches the record's `name`:

```python
@fairdm.register
class WaterSampleConfig(BaseSampleConfiguration):
    model = WaterSample
    fields = ["name", "water_source", "ph_level"]
    search_fields = ["name", "water_source"]
```

Two kinds of declaration are refused when the server starts, rather than on the first search a
visitor types. A path that names no field on the model is one. The other is a path that resolves
to a field a substring match cannot read: a number, a boolean, a date or a geometry. So
`search_fields = ["ph_level"]` on a `DecimalField` raises `FieldValidationError` at start-up,
naming the configuration and the field.

**A searchable field you add is yours to index.** The framework indexes `name`, because that is
what it searches when you declare nothing. Any other field you name in `search_fields` is searched
with an unanchored `LIKE`, and on a table of any size that is a sequential scan unless you index
it yourself:

```python
class WaterSample(Sample):
    water_source = models.CharField(
        max_length=200,
        db_index=True,
        verbose_name=_("water source"),
        help_text=_("Where the sample was drawn from."),
    )
```

Adding the index is a schema change, so it needs a migration like any other field change.

## Addresses and collisions

A listing's address and URL name both come from the model's own name, so two registrations whose
models share a name would collide. That is refused at start-up with an error naming both models
and the address they contend for, rather than one listing silently shadowing the other.

Reverse a listing's address by its URL name:

```python
from django.urls import reverse

reverse("rocksample-list")
```
