# Feature Specification: The columns of a sample or measurement type

**Feature Branch**: `039-table-columns`

**Created**: 2026-11-23

**Status**: Draft

**Goals**: G11: round-trip import and export of tabular data. G2: registering a model is enough to
get a working portal surface. G10: data and metadata are reachable by machines through a documented
API.

**Roadmap**: R21, tabular data goes in and comes back out. This is the first of its three features.
Export is #696 and import is #697, and both read their columns from this one.

**Input**: #695. Every registered sample and measurement type says what a spreadsheet of its records
holds: the columns, in order, and what each one accepts. A developer asks a type for this with
`get_table_schema()`, next to `get_resource_class()`. A person downloads it for any type as a
[Frictionless Table Schema](https://specs.frictionlessdata.io/table-schema/), and reads it as a guide
to the columns. The design comes from the prototype recorded on #692, which the maintainer has seen
and accepted.

## What exists, and what this specification changes

A registered type's `ModelConfiguration` offers `get_resource_class()`, a django-import-export
resource generated by the registry. Nothing reaches it from a page, and its columns are incomplete:
it carries no portal ID and no Local ID, so a file read through it cannot find the records it came
from, and for some types it leaves out the sample. Nothing in the portal says what a file of a type's
records should hold, and nothing publishes it for a machine to read.

After this feature:

- Every registered sample and measurement type has a **table schema**: its columns, in order, each
  with what it holds and how a cell of it is written. A developer gets it from the type's
  configuration with `get_table_schema()`.
- Every column reads a spreadsheet cell into the value its field stores, and writes that value back
  as a cell the same column reads.
- An **import definition** names a kind of file and says what it holds. FairDM builds one for every
  registered type, named after it, and a developer looks one up by name. A project can register its
  own.
- Each type's table schema can be downloaded as a Frictionless Table Schema from an address of its
  own.
- The **column guide**, a component that lays out a type's columns for a person to read, is ready
  for the pages that need it.

`get_resource_class()` and the registry's generated resource are unchanged by this feature. The
import (#697) replaces them.

## Boundary

- **Exporting a table's rows** (the Export menu, the formats, the Excel workbook with the guide and
  the lists of allowed values inside it, the `sample_name` cells an export fills) is #696. It reads
  its columns from this feature.
- **Importing a file** (the import pages, matching a file's headings to columns, the options for what
  a file may do, the check, the import, undo, the import record) is #697. It reads its columns and
  its cells from this feature. Placing the column guide and a link to the Table Schema on the import
  page is #697's.
- **The Import data button on an empty dataset's overview** is #698, outside every specification.
- **Several types in one file**, and importing keywords, tags, descriptions, dates, identifiers or
  contributors, are later features.
- **A project's own import definitions** can be registered, but no page uses one yet. Anything a
  particular portal needs from them waits until that portal moves to this workflow.
- **The API** (specification 011) is unchanged. The Table Schema is served at an address of its own.

## Clarifications

### Session 2026-11-23

The feature was agreed from the prototype the maintainer has seen and accepted (#692) and from #695,
and each question was answered from them without putting it to him again. The longer reasoning is in
[decisions.md](decisions.md).

- Q: Which columns does a type have, and in what order? → A: The portal ID, the Local ID, the name,
  and for a measurement the sample it was made on and the sample's name. Then the type's own fields
  in the order the model declares them. Then, for a sample, its status, and for both kinds the four
  location columns: latitude, longitude, elevation and location uncertainty.
- Q: What does `resource_fields` change? → A: A type with no `resource_fields` gets every field a
  person can type into a spreadsheet. A type with `resource_fields` gets those, plus the identifiers
  and every field a new record cannot be saved without. Status and the location columns are kept
  only when `resource_fields` names them.
- Q: Is the column's heading its label? → A: No. The heading is the field's name, so a file keeps the
  same headings when the portal's labels are translated or reworded. The label, the label without its
  unit and a column's listed alternatives are the other headings it is recognised by.
- Q: Who may download a type's Table Schema, and where? → A: Anyone, from an address that depends on
  the type alone. It describes the type, holds no record of anyone's, and a person preparing a file
  may not yet have a dataset.
- Q: Where does a column's example come from? → A: From the column's type and constraints, never from
  a stored record. The prototype took examples from the first stored record of the type, which would
  show a private record's values to anyone reading the schema or the guide.
- Q: Does the Table Schema list every allowed value of a long list? → A: Yes. The guide may show part
  of a long list, but the Table Schema lists every value a cell of the column may hold as an export
  writes it, so a machine can check a file against it.
- Q: What does a cell naming a sample the person may not see get? → A: The same refusal as a sample
  that does not exist, so a cell tells nobody that a private sample exists.
- Q: The prototype's guide draws its tables with table roles on plain elements. Is that kept? → A: The
  guide must be read by assistive technology as one table per group of columns, with its column
  headers. Whether it is drawn as a native table or keeps the roles is decided when it is built,
  checked with an accessibility audit, and it keeps the prototype's look either way.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A developer asks a type for its columns (Priority: P1)

A developer building on FairDM, or on a portal's own sample and measurement types, needs to know what
a file of a type's records holds: to write it, to read it, or to show a person what it should hold.
They ask the type's configuration for its table schema and get every column in order, each saying
what it holds, how a cell of it is written and whether a new record needs it. They read cells into
field values and write values back as cells with the columns' own widgets. They look up the import
definition of a type by name, register one of their own, and place the column guide of a type on a
page.

**Why this priority**: this is the foundation of R21. Export and import both read their columns from
here, and a file exported by one can only be imported by the other if both use the same columns.

**Independent Test**: for a sample type and a measurement type of the demo portal, one with
`resource_fields` and one without, ask for the table schema and compare its columns with the model.
Read a cell of every kind through its column's widget, write the value back and read it again. Look
up each type's import definition, register another, and render the column guide of each type.

**Acceptance Scenarios**:

1. **Given** a registered sample type with no `resource_fields`, **When** a developer asks its
   configuration for its table schema, **Then** they get, in order, the portal ID, the Local ID, the
   name, every field of the type's own a person can type into a spreadsheet in the order the model
   declares them, the status, and latitude, longitude, elevation and location uncertainty.
2. **Given** a registered measurement type, **When** a developer asks for its table schema, **Then**
   it carries the sample the measurement was made on after the name, followed by a column for the
   sample's name that is marked as written on export and never read on import, and it carries no
   status.
3. **Given** a type whose configuration lists `resource_fields`, **When** a developer asks for its
   table schema, **Then** it holds those fields, the portal ID, the Local ID, and every field a new
   record of the type cannot be saved without, even one the list leaves out. Status and the location
   columns appear only when the list names them.
4. **Given** any column of a table schema, **When** a developer reads it, **Then** it gives its
   heading, its label, the other headings it is recognised by, what kind of value it holds, its unit,
   its range, its allowed values, whether a new record needs it, what it holds in words, and an
   example of a cell. Where a field's label ends with a unit in brackets, the unit is the column's
   and the label without it is one of the headings it is recognised by.
5. **Given** a column's heading, **When** the portal's language changes or a label is reworded,
   **Then** the heading stays the field's name.
6. **Given** a type with records stored in any dataset, private or not, **When** a developer reads
   its columns' examples, **Then** none of them is a value taken from a stored record.
7. **Given** a column of each kind (text, whole number, number, yes or no, date, date and time, time,
   a date as precise as known, one of a fixed set of choices, a concept from a vocabulary, a sample,
   a number with a unit, latitude and longitude), **When** a developer reads a well-formed cell
   through the column's widget, **Then** they get the value the field stores, and writing that value
   back gives a cell the same widget reads to the same value.
8. **Given** a cell that does not fit its column (text where a number belongs, a value outside the
   column's range, more decimal places than the field holds, a value not in the allowed list, a date
   in another form), **When** it is read through the column's widget, **Then** it is refused with a
   reason a person can act on. **Given** a number written with a decimal comma, **Then** it is
   refused, never guessed at, and the reason gives the same number written with a point.
9. **Given** a concept column, **When** a cell holds the concept's label in any language the
   vocabulary gives, its code or its web address, **Then** it reads as that concept.
10. **Given** a sample column, read for a dataset and a person, **When** a cell holds the portal ID of
    a sample the person may see, **Then** it reads as that sample, whichever dataset holds it.
    **When** it holds the Local ID or a name unique within that dataset, **Then** it reads as that
    dataset's sample. **When** it names a sample the person may not see, or one that does not exist,
    **Then** the refusal is the same for both. **When** a Local ID or name is shared by more than one
    sample in the dataset, **Then** it is refused with a reason that asks for the portal ID.
11. **Given** a number-with-a-unit column, **When** a cell holds a bare number, **Then** it reads in
    the column's unit. **When** it holds a number and a compatible unit, **Then** it reads as that
    quantity in the column's unit. **When** the unit is not compatible, **Then** it is refused.
12. **Given** the registered types of a portal, **When** a developer looks up an import definition by
    the name of a type, **Then** they get the definition FairDM built for it, which gives that type's
    table schema, the kind of record it fills and the file formats it is offered in. **When** they
    look up a name nobody registered, **Then** they get nothing, not an error. **When** they ask for
    every definition of one kind, **Then** they get only the sample types' or only the measurement
    types'.
13. **Given** a developer's own import definition, **When** they register it under a new name,
    **Then** looking that name up gives it. **When** they register it under a name already known,
    **Then** the registration is refused with a reason.
14. **Given** a type's table schema, **When** a developer places the column guide component for it on
    a page, **Then** the guide lays out every column in groups (identifying the record, the type's
    own fields, the fields every sample or measurement has), each column with its heading, its label,
    whether a new record needs it or whether it finds the record, what it holds, the other headings
    it is recognised by, how a cell is written, its range, its allowed values and its example.
    Assistive technology reads each group as a table with its column headers.
15. **Given** a portal's own sample or measurement type, **When** it is registered, **Then** it has a
    table schema, an import definition and a guide with no further work by the portal's developer.

### User Story 2 - A person downloads a type's Table Schema (Priority: P2)

A researcher preparing a spreadsheet for a portal, a data manager checking files before sending
them, or a script they wrote, wants the columns of a sample or measurement type in a form a machine
reads. They open the address of the type's Table Schema and get it as a Frictionless Table Schema,
which standard tools use to check a file before it is imported.

**Why this priority**: the guide tells a person what a file holds. The Table Schema lets a tool tell
them whether a file they have actually holds it, before they upload it anywhere.

**Independent Test**: for a sample type and a measurement type, open the address of the Table Schema
without signing in, check what kind of file the answer is and validate it as a Frictionless Table
Schema. Then write a file of a few records in the columns' own cell form and check it against the
schema with a standard Frictionless validator. Open the address of a type that is not registered.

**Acceptance Scenarios**:

1. **Given** a registered type, **When** anyone opens the address of its Table Schema, signed in or
   not, **Then** the answer is the type's table schema as a valid Frictionless Table Schema, marked as
   JSON, and a browser saves it as a file named after the type.
2. **Given** that Table Schema, **When** it is read, **Then** it holds every column of the type's
   table schema in the same order, each with its heading as the field's name, its label as the
   field's title, what it holds as its description, its type, its unit, and its constraints: whether
   a new record needs it, its length, its range and its allowed values.
3. **Given** a column with a list of allowed values, **When** the Table Schema is read, **Then** it
   lists every value a cell of the column may hold as an export writes it, however long the list.
4. **Given** the column written on export and never read on import, **When** the Table Schema is
   read, **Then** it carries that column and says it is not read on import.
5. **Given** the Table Schema, **When** it is read, **Then** the portal ID is its primary key, and an
   empty cell is its missing value.
6. **Given** a file of records written in the columns' own cell form, **When** it is checked against
   the type's Table Schema with a standard Frictionless validator, **Then** it is valid. **Given** a
   file with a cell outside its column's range, or not in its allowed list, **Then** the validator
   reports it.
7. **Given** the address of a type that is not registered, **When** anyone opens it, **Then** they get
   the portal's not-found answer.
8. **Given** a portal in a language other than English, **When** its Table Schema is read, **Then**
   the titles and descriptions are in the portal's language, and the field names are the same as in
   English.

---

### Edge Cases

- A type with no stored records has the same columns, examples and Table Schema as one with many.
- A concept column whose vocabulary is empty has no allowed values. Its cells are refused with a
  reason, and its Table Schema says it allows none.
- A required field the developer left out of `resource_fields` is still a column, and is marked as
  needed for a new record, so a file of new records can always be saved.
- A field that only the portal sets (its record ID, the type, when it was added and changed, its
  dataset, its image, its keywords and tags) is never a column. The stored location is offered as
  latitude and longitude, never as one value.
- A cell with spaces around its value reads as the value without them. An empty cell reads as no
  value. What an empty cell does to a stored record is the import's to decide (#697).
- A date written as a spreadsheet's own date reads the same as one written as text.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Every registered sample and measurement type's configuration MUST offer
  `get_table_schema()`, next to `get_resource_class()`, giving the type's columns in order. A portal's
  developer MUST be able to override it, as with the configuration's other components. (US1)
- **FR-002**: The columns MUST be, in order: the portal ID; the Local ID; the name; for a measurement
  the sample and a column for the sample's name; the type's own fields in the order the model declares
  them; for a sample its status; latitude, longitude, elevation and location uncertainty. (US1)
- **FR-003**: A type with no `resource_fields` MUST get every field a person can type into a
  spreadsheet. A type with `resource_fields` MUST get those, the identifiers and every field a new
  record cannot be saved without. Status and the location columns MUST appear only when its
  `resource_fields` names them or it has none. Fields only the portal sets MUST never be columns.
  (US1)
- **FR-004**: Every column MUST give its heading, label, other recognised headings, kind of value,
  unit, range, allowed values, whether a new record needs it, a description and an example. The
  heading MUST be the field's name and MUST NOT change with the portal's language or the field's
  label. A unit given in brackets at the end of a field's label MUST become the column's unit, and the
  label without it one of the recognised headings. (US1)
- **FR-005**: A column MUST say whether it finds the record (portal ID, Local ID), is read on import,
  or is written on export and never read on import (the sample's name). (US1, US2)
- **FR-006**: No column's example MUST be taken from a stored record. (US1)
- **FR-007**: Each kind of column MUST have a widget that reads a cell into the value its field
  stores and writes a stored value back as a cell the same widget reads to the same value. The kinds
  are text, whole number, number, yes or no, date, date and time, time, a date as precise as known, a
  fixed set of choices, a concept, a sample, a number with a unit, latitude and longitude. (US1)
- **FR-008**: A widget MUST refuse a cell that does not fit its column, with a reason a person can act
  on, and MUST refuse a number written with a decimal comma, giving the number written with a point,
  rather than guess at it. (US1)
- **FR-009**: A concept cell MUST read by the concept's label in any language the vocabulary gives, by
  its code or by its web address. A number-with-a-unit cell MUST read a bare number in the column's
  unit and a number with a compatible unit converted to it. (US1)
- **FR-010**: A sample cell MUST read by the portal ID of any sample the person may see, or by a Local
  ID or a name unique within the dataset it is read for. A sample the person may not see MUST be
  refused exactly as one that does not exist. A Local ID or name shared within the dataset MUST be
  refused with a reason that asks for the portal ID. (US1)
- **FR-011**: FairDM MUST build one import definition for every registered sample and measurement
  type, named after the type, giving its table schema, the kind of record it fills and the file
  formats it is offered in. (US1)
- **FR-012**: A developer MUST be able to look up an import definition by name, getting nothing for a
  name not known, and to list every definition or those of one kind. (US1)
- **FR-013**: A developer MUST be able to register their own import definition under a new name. A
  name already known MUST be refused. (US1)
- **FR-014**: The column guide MUST be a Cotton component that, given a type's table schema, lays out
  every column in its group with the information FR-004 and FR-005 list. Assistive technology MUST
  read each group as a table with its column headers. (US1)
- **FR-015**: A portal's own registered types MUST get their table schema, import definition, widgets
  and guide with no work by the portal's developer. (US1)
- **FR-016**: Every registered type's table schema MUST be served as a Frictionless Table Schema at an
  address that depends on the type alone, to anyone, marked as JSON and saved by a browser as a file
  named after the type. An address for a type that is not registered MUST answer not found. (US2)
- **FR-017**: The Table Schema MUST hold every column in order, each with its heading as the name, its
  label as the title, its description, its type, its unit and its constraints (needed for a new
  record, length, range, every allowed value as an export writes it). It MUST name the portal ID as
  its primary key and the empty cell as its missing value, and MUST say which column is not read on
  import. It MUST be valid against the Frictionless Table Schema specification. (US2)
- **FR-018**: A file written in the columns' own cell form MUST validate against the type's Table
  Schema with a standard Frictionless validator. (US2)
- **FR-019**: Labels, descriptions and reasons MUST be translatable, and headings MUST NOT be
  translated. (US1, US2)

### Key Entities

- **Table schema**: the columns of one registered sample or measurement type, in order. Worked out
  from the type's model and configuration each time it is asked for. Not stored.
- **Column**: one column of a type's file, with its heading, label, recognised headings, kind, unit,
  range, allowed values, whether a new record needs it, what it holds and an example, and the widget
  that reads and writes its cells.
- **Import definition**: a named kind of file: the record type it fills, its table schema, and the
  formats it is offered in. FairDM builds one per registered type. A project can register its own.
  Not stored. An import record (#697) keeps the definition's name.
- **Table Schema**: the table schema written in the Frictionless Data standard, served at an address
  of its own for each type.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Every sample and measurement type registered in the demo portal, and any a portal adds,
  has a table schema, an import definition, a guide and a Table Schema, with no code written for the
  type.
- **SC-002**: Every value a column's widget writes is read back by the same widget to the same value,
  for every kind of column.
- **SC-003**: Every registered type's Table Schema is valid against the Frictionless Table Schema
  specification, and a file written in its columns' cell form validates against it with a standard
  validator.
- **SC-004**: Neither the guide, the Table Schema nor any widget's refusal tells anyone anything about
  a record they may not see.
- **SC-005**: An accessibility audit of the column guide reports no table without headers.

## Assumptions

- Main is on django-mvp 0.36 and django-mvp-forms 0.11 (#693), the versions the prototype was built
  on.
- django-import-export, tablib and openpyxl stay the libraries exports and imports are built on. The
  widgets are django-import-export widgets.
- A type's model name is unique across the portal's registered types, as the registry already
  assumes for its addresses.
